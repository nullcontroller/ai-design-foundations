# AI Design Foundations

LLM / RAG / QAシステムを、  
**再現性・説明責任・HITLを前提に実務へ組み込むための設計原則と検証ログ**です。

本リポジトリでは、生成AIを単なるコード生成やプロンプト操作の対象としてではなく、

> **確率的に出力を生成するコンポーネントとして、システム全体の中でどう制御するか**

という観点から整理しています。

AIに判断を丸投げするのではなく、

- 何をAIへ任せるか
- どこまでAI出力を信頼するか
- どこで人間が確認するか
- 根拠をどう残すか
- 複数のAIをどのように役割分担させるか

まで含めて、AIを実務で継続利用できる構造を考えています。

| AI品質 | ハルシネーション対策、検証可能性、説明責任 |

## Design Principles

### AIは理解している前提で設計しない

LLMは、人間と同じ意味で内容を理解して判断しているわけではありません。

そのため、AI自身の「注意深さ」や「正しさ」に依存するのではなく、  
**誤りが発生することを前提にシステム側で制御する**ことを重視しています。

### 推測させない

必要な情報が存在しない場合に、AIがもっともらしい回答を生成することを防ぎます。

- 参照可能な知識範囲を限定する
- 根拠を要求する
- 根拠が存在しない場合は回答させない
- 推測と確認済み情報を区別する

### 判断責任をAIへ移さない

AIは候補や論点を提示できます。

一方で、品質や責任に直結する判断については、人間または組織が最終判断を持つよう設計します。

### AI出力はリスクに応じて扱う

すべてのAI出力を同じ強度でレビューする必要はありません。

例えば、

| 出力 | 扱い |
|---|---|
| 次工程へ渡すプロンプト | 後工程で検証可能なら積極利用 |
| 構成案・調査観点 | 候補として利用 |
| PlantUML・仕様書 | 人間が内容を確認 |
| コード上の事実 | 必ず実コードと照合 |
| 最終要件・責務範囲 | 人間が決定 |
| 生成コード・テスト結果 | 必ず検証 |

というように、誤りの影響に応じて確認強度を変えます。

> **後工程で検証できる中間成果物は積極的に利用し、品質や責任に直結する判断は人間が検証する**

ことを基本原則としています。

## AI Orchestration

生成AIごとに、得意な情報や作業は異なります。

そのため、一つのAIへすべてを任せるのではなく、  
**AIごとの強みを理解し、一つの工程として接続する**ことを重視しています。

実務では、例えば次のように役割を分担しています。

| 担当 | 役割 |
|---|---|
| GPT | 前提・制約から論点や設計案を整理する |
| GitHub Copilot | コードを意味から探索し、実装や影響範囲を具体化する |
| Microsoft 365 Copilot | 確認済みの内容をOffice成果物へ反映する |
| 人間 | 前提、責務、優先順位、品質、最終判断を担う |

重要なのは、AIを複数使うこと自体ではありません。

> **AIは、それぞれ強みが違う。  
> その強みを理解し、適切な役割を与え、一つの工程としてオーケストレーションする。**

ことが重要だと考えています。

## Repository Structure

### 100. 数学から見たAI

LLMを確率的なモデルとして理解するための基礎を整理しています。

プロンプトのテクニックではなく、  
**なぜ出力が揺れるのか、なぜハルシネーションが発生するのか**を構造から考えます。

### 200. QAチャット設計思想

RAG / QAシステムを安全に利用するための設計原則を整理しています。

主なテーマは、

- 知識境界
- 回答制約
- 根拠提示
- HITL
- ハルシネーション対策
- 責務分離

です。

### 300. プロンプト構造

プロンプトを単なる文章ではなく、  
**AIへ制約条件と役割を与えるインターフェース**として整理しています。

### 400. コード生成

生成AIをソフトウェア開発へ組み込む際の考え方を整理しています。

コード生成そのものよりも、

- 既存コードの理解
- 変更影響の確認
- 実装候補の生成
- 人間によるレビュー
- テスト
- 最終的な品質責任

まで含めた開発プロセスを重視しています。

## Case Studies

設計思想だけでなく、実際の業務適用についても整理しています。

### 3つのAIをオーケストレーションしたレガシー保守

レガシーシステムの完全化保守において、

**GPT → GitHub Copilot → Microsoft 365 Copilot**

を役割分担させ、要件整理から仕様化、コード修正、単体テストまでを一つの工程として設計した事例です。

主なポイントは、

- GPTによる設計論点の整理
- GitHub Copilotによる既存コードの意味検索
- Microsoft 365 CopilotによるExcel仕様化
- PlantUMLを利用したAI間の仕様受け渡し
- 人間によるコード・仕様の検証
- 最小変更によるレガシー保守
- AI出力をリスクに応じて扱う設計

です。

結果として、従来必要だった外部委託を行わず、  
想定開発期間を約7割短縮しました。

## What I Value

生成AIの価値は、単に「作業を自動化すること」ではないと考えています。

重要なのは、

**AIによって人間の判断能力と設計能力を拡張すること**

です。

そのため、

- AIに何を任せるか
- AIに何を任せないか
- AI間で何を受け渡すか
- どこで人間が確認するか
- 最終的な責任を誰が持つか

まで含めて設計します。
