# AIオーケストレーション

生成AIは、それぞれ得意な情報・作業・出力形式が異なる。

そのため、一つのAIへすべてを任せるのではなく、
**AIごとの強みを理解し、適切な役割を与え、一つの工程として接続すること**を重視する。

本章では、複数のAIを単に併用するのではなく、設計・開発工程としてオーケストレーションするための考え方を整理する。

---

## 基本思想

AIオーケストレーションで重要なのは、利用するAIの数ではない。

重要なのは、

- どのAIに何を任せるか
- どのAIに何を任せないか
- AI間で何を受け渡すか
- どの形式で情報を受け渡すか
- どこで人間が検証するか
- 最終判断を誰が持つか

を工程として設計することである。

> **AIは、それぞれ強みが違う。  
> その強みを理解し、適切な役割を与え、一つの工程としてオーケストレーションする。**

---

## AIごとに役割を分ける

例えば、ソフトウェア開発では次のように役割を分けられる。

| 担当 | 主な役割 |
|---|---|
| GPT | 前提・制約・論点の整理、設計候補の比較 |
| GitHub Copilot | 既存コードの探索、呼出し関係・影響範囲の確認、実装候補の生成 |
| Microsoft 365 Copilot | 確認済み情報のExcel・文書への構造化 |
| 人間 | 前提設定、責務分離、設計判断、品質確認、最終承認 |

AIは万能な主体ではなく、工程内のコンポーネントとして扱う。

---

## AI間では「確認済みの構造」を渡す

AIからAIへ情報を渡す場合、単なる自然言語の要約だけでは、処理順序・分岐・呼出し関係などの構造が失われやすい。

そのため、情報の性質に応じて中間成果物を使い分ける。

| 情報 | 適した形式 |
|---|---|
| 前提・制約・要求 | 自然言語 |
| 実装上の事実 | ソースコード |
| 処理順序・分岐・呼出し関係 | PlantUMLなどの構造表現 |
| 要件・判断理由・影響範囲・試験観点 | Excel等のレビュー可能な仕様書 |

重要なのは、AIが生成した成果物をそのまま次のAIへ渡すことではない。

**人間が確認した構造を、次工程のAIへ受け渡す**ことで、誤りの連鎖を抑える。

---

## オーケストレーション例

実務では、次のような流れを取ることができる。

```text
人間
  ↓ 前提・制約・品質基準を定義
GPT
  ↓ 論点・設計候補・トレードオフを整理
人間
  ↓ 方針を決定
GitHub Copilot
  ↓ コードから実装事実・影響範囲を確認
GPT
  ↓ 構造をPlantUML等へ整理
人間
  ↓ コードと照合し、構造を確認
Microsoft 365 Copilot
  ↓ 確認済み構造を仕様書へ反映
人間
  ↓ 仕様をレビュー
GitHub Copilot
  ↓ 実装候補を生成
人間
  ↓ コードレビュー・テスト
```

この流れでは、人間は単なる承認者ではない。

**工程全体の制約・責務・品質を設計する主体**として位置付ける。

---

## 一つのAIにすべてを任せない理由

一つのAIに要件整理、コード調査、仕様化、実装、評価まで任せると、同じ誤認識が後工程へそのまま伝播する可能性がある。

複数AIを役割分担させる目的の一つは、単なる効率化ではなく、
**異なる表現・異なる工程を通じて認識を再構成し、人間が検証できる地点を増やすこと**にある。

したがって、AIオーケストレーションでは「自動化率」よりも、

- 検証可能性
- 誤りの局所化
- 責務の明確化
- 成果物の再利用性

を重視する。

---

## AI出力の信頼度は工程で決める

AI出力をすべて同じ強度で確認する必要はない。

| 出力 | 扱い |
|---|---|
| 調査候補・論点 | 候補として積極利用 |
| 次工程用プロンプト | 後工程で検証できるなら利用 |
| PlantUML・仕様書 | 人間が内容を確認 |
| コード上の事実 | 実コードと照合 |
| 最終要件・責務範囲 | 人間が決定 |
| 生成コード・テスト結果 | 必ず検証 |

> **後工程で検証できる中間成果物は積極的に利用し、品質や責任に直結する判断は人間が検証する。**

---

## 目的

AIオーケストレーションの目的は、AIを増やすことではない。

**AIごとの特性を利用して、人間が設計・判断・レビューしやすい工程を作ること**である。

AIを使うのではなく、
AIの強み・弱み・出力形式・検証方法まで含めて工程を設計する。
